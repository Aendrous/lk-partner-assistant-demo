# Принятые решения: пайплайн и автозапуск AI-KB

Дата фиксации: 2026-08-22

## Задача

Обучать ассистента IntraService из закрытых заявок, **но только когда в WEBKB не было готового ответа**, с возможностью **отключить автозапуск** и **не дублировать** инструкции.

## Решения

### 1. Master switch выключен по умолчанию

`auto_learn_kb: false` в `config/settings.default.json`.

Автосоздание черновиков **не включается** без явного действия оператора (UI или env).

### 2. Два триггера обучения

| Триггер | Настройка | По умолчанию |
|:--|:--|:--|
| При разборе заявки | `auto_learn_on_analyze` | **off** |
| При закрытии (watch) | `auto_learn_on_close` | **on** (если master on) |

**Почему:** при разборе исполнитель ещё работает; финальное решение может появиться в комментариях только после закрытия.

### 3. Не учить, если чатбот уже нашёл KB

`skip_if_kb_found: true`

Условие: `has_kb_solution=true` **и** есть ссылки на Confluence в `article_links`.

**Почему:** повторная инструкция не нужна; последующая проверка при закрытии тоже пропускается.

### 4. Не дублировать черновики

`skip_if_draft_exists: true`

Если в `knowledge/learned/index.json` уже есть запись со статусом `draft|reviewed|published` — не создавать новую.

**Неполная / похожая инструкция:** `semantic_dedup_enabled` → при score ≥ supplement:

| Match | Действие |
|:--|:--|
| **corpus / published** | новый review-черновик `supplement` (Promote позже append) |
| **in_review / draft** (в т.ч. сам supplement) | **правка того же черновика** (`update_in_place`), без `HD-09-SUP-SUP-…` |
| score ≥ duplicate на in_review | skip (уже покрыто), force → update_in_place |

`target_page_id` всегда из `target_for_contour(service_key)` (`kb_assistant_pages.json`), не из pageId в тексте matched draft.

Черновик содержит блок **«Решение IEK LLM»** + маркеры `<!-- KB_INSERT_START/END -->`; Promote вставляет только этот текст.

### 5. Принудительное обучение (--learn / UI)

Обходит `skip_if_kb_found`, но **не** обходит `skip_if_draft_exists` (защита от дублей).

Для нового сценария при наличии общей статьи KB (пример: #696965 API ключ).

### 6. Настройки: UI + local json + env

| Источник | Приоритет |
|:--|:--|
| `config/settings.local.json` | после defaults |
| `INTRASERVICE_AUTO_LEARN_*` env | поверх local |

UI: `streamlit run app.py` → sidebar → «Сохранить настройки».

### 7. Артефакты каждого прогона

`pipeline/runs/{run_id}/` — manifest, steps, analysis.json.

Включение: `pipeline_save_runs` (default on).

### 8. Публикация в Confluence — только после ревью

Автопipeline **останавливается на черновике** `docs/черновики_статей/`.

Дальше вручную: ревью → `publish_kb_draft_confluence.py` → `build_bp_corpus.py`.

### 9. Отдельная ветка Confluence (план)

Child под pageId **124630073**: «Чатбот IntraService: база быстрых ответов (AI-KB)».

Append блоков bp → **124629661**. Конфиг: `docs/confluence/kb_assistant_pages.json`.

### 10. Skip при «В процессе» / «Ожидание ответа» (2026-08-24)

`skip_if_in_progress_or_awaiting: true` (default).

Если take / watch_overdue и StatusId ∈ {27, 46, 120} **и нет** свежей эскалации «До просрочки»:
**полный skip**.

**Исключение — есть уведомление о просрочке:** анализ + скрытый комментарий (файл `_analysis_*.json` / pipeline/runs) + **Deadline +1 день** + **открытый** комментарий заявителю. Статус не меняем.

Настройки: `overdue_shift_deadline`, `overdue_post_public`. Watch смотрит также статусы 27/46/120.

### 10a. Автопост скрытых + заметка AI-KB (2026-08-25)

`auto_post_comment: true` (local) — watch_new / reply / overdue пишут **скрытый** разбор.

`post_learn_note: true` — при создании черновика AI-KB в заявку добавляется скрытая строка:
«на основе заявки создан черновик …» + ссылка на целевую страницу Confluence.
При разборе с `--post` заметка вшивается в тот же скрытый комментарий; при `pipeline_watch` — отдельным скрытым комментарием.

`auto_take_in_work` по умолчанию **false** (не забирать заявки у очереди без явного включения).

### 10b. Черновики в Confluence для общей правки (2026-08-25)

Personal draft Confluence через REST для всей команды **недоступен** (это личные черновики автора).

Рабочий обход:
1. `auto_push_confluence_draft: true` → страница с человеческим title (`BP-06. …`) под **«статьи самообучения (ревью)»** (метка `ai-kb-draft`).
2. Команда правит страницу в Confluence UI.
3. `sync_kb_after_review.py --task-id <id>` читает тело из Confluence, append в «Быстрые ответы», метка `ai-kb-published` (без `[ОПУБЛИКОВАНО]` в title), rebuild corpus + OWUI.

```powershell
python scripts/push_kb_draft_confluence_review.py --init-parent
python scripts/push_kb_draft_confluence_review.py --all-pending
```

Не путать с append в боевые KB-страницы: ревью-папка ≠ «Быстрые ответы».

### 10c. L1 Simple + public только при KB (2026-08-25)

UI sidebar: 5 главных тумблеров; остальное в «Расширенные».

`public_reply_only_if_kb: true` — открытый комментарий при просрочке только если
`has_kb_solution` + шаги/ссылки, или уже был prior public, или явный факт 1С «резерв в пути».
Иначе — только скрытый разбор (без воды «уточните…» в публичку).

`auto_take_in_work: false` — take только из `watch_overdue`.

Статьи самообучения: заголовки без `[ЧЕРНОВИК]`/`[ОПУБЛИКОВАНО]`; статус через labels;
папка pageId 124640307 переименована в «…статьи самообучения (ревью)»; MD→storage с inline **bold** и ссылками.

### 10d. Ответ заявителя и обогащение разбора (2026-08-26)

`watch_user_reply` **не** делает переразбор LLM; пишет только короткий **скрытый** комментарий с правилом.

| Сигнал | Действие |
|:--|:--|
| Заявитель «спасибо / помогло / можно закрывать» | статус **29** «Выполнена» + скрытый «Пользователь подтвердил решение» |
| Уточнение / «не помогло» / доп. вопрос (из 46/120) | статус **38** + скрытый комментарий с правилом |
| Повторный вопрос исполнителя про актуальность (≥20 ч после первого ответа), статус 46 | статус **120** + скрытый комментарий с правилом |
| Нейтральный текст / ответ без сигнала | игнор |

Первичный скрытый разбор (`analyze` / `watch_new`) дополняется:

1. **Предыдущие обращения инициатора** — тема из **описания** заявки (не сырое Name письма)
2. **Похожие заявки по смыслу** — кандидаты из поиска + отбор **LLM** по описанию и публичной переписке (не по общему слову «склад»)
3. **Ответ для вставки** — `public_reply_draft_ru` + `kb_refs` (конкретный раздел/проблема и URL); локальные черновики `docs/черновики_статей` и корпус ЛК/БП/1С в промпте. Шапка страницы «Назначение: быстрые ответы…» отбрасывается.

### 11. Связанные заявки (дубли по документу)

`link_related_on_post` + `add_parent_creator_as_observer`.

Ключи: заказ, счёт, эл.заявка, GUID ЛК. Поздняя → `ParentId` ранней; Creator ранней → Observer поздней.

## Алгоритм `should_auto_learn`

```
if 1С: запрос на изменение (1010) или уже в работе (27) → skip (жёстко)
if force and draft_exists → skip (duplicate)
if force → run
if not auto_learn_kb → skip
if skip_if_kb_found and KB found → skip
if skip_if_draft_exists and draft exists → skip
if trigger=watch_close:
    if not auto_learn_on_close → skip
    if require_closed and not closed → skip
if trigger=analyze:
    if not auto_learn_on_analyze → skip
if no kb_gap → skip
→ run (create draft)
```

После `should_auto_learn` в `learn_from_task_data` при `require_closed_for_auto_learn`
ещё проверяется, что решение взято из **публичного ответа исполнителя**
(`performer_resolution_present`), а не из fallback на `summary_ru`/название заявки.

## Сверка с индустрией (2024–2026)

Наш baseline совпадает с паттерном **closed-loop knowledge capture** (Intercom Fin, Zendesk Knowledge Builder, AWS KnowledgeForge, Box): gap → черновик → HITL → публикация → corpus.

| Практика | У нас | Типично в индустрии |
|:--|:--|:--|
| HITL перед публикацией | ✅ черновик → ревью | ✅ draft-only |
| Master switch off by default | ✅ | ✅ risk-tiered |
| Skip if KB found | ✅ `has_kb_solution` | ✅ gap detection |
| Dedup by task_id | ✅ index.json | + semantic similarity |
| Learn on close, not on analyze | ✅ watch | ✅ accumulation after resolve |
| Step artifacts | ✅ `pipeline/runs/` | + Langfuse для LLM |
| Per-ticket draft | ✅ | grouping 3+ похожих тикетов |

**Источники:** [Intercom Fin Suggestions](https://fin.ai/research/generating-knowledge-center-content-from-customer-service-conversations/), [KnowledgeForge (AWS)](https://aws.amazon.com/blogs/machine-learning/knowledgeforge-mining-gold-from-the-itsm-ticket-graveyard/), [Box closed-loop KB](https://blog.box.com/building-closed-loop-knowledge-system-ai-powered-it-support-box), [LangGraph HITL](https://langchain-ai.github.io/langgraph/concepts/human_in_the_loop/).

## Roadmap (не в v1)

1. ~~**Semantic dedup**~~ — Jaccard/overlap в `kb_dedup.py` + lifecycle in_review.
2. ~~**Edit vs Create**~~ — `update_in_place` для in_review; `supplement` review только после published/corpus.
3. **Lifecycle в index** — `merged_into | approved | rejected` + `rejection_reason` (частично: merged_into).
4. ~~**Weekly gap digest**~~ — `scripts/weekly_gap_digest.py` + Task Scheduler (вс).
5. **Observability LLM** — опционально Langfuse на `_chat()` (cost/latency); бизнес-артефакты остаются в `pipeline/runs/`.
6. **Accumulation** — группировать 3+ похожих закрытых тикета перед генерацией (Intercom: 12% → 60% approval).

### Антипетля watch_new (2026-08-25)

Симптом #696928: скрытый разбор «Сервис HD:…» каждые ~15 мин.

Причина: пост чатбота обновляет `Changed` → `watch_new` считал заявку новой и постил снова.

Исправление:
1. Если уже `posted` — повторный прогон только при **новом комментарии не-бота**.
2. После поста в `seen_new` пишется актуальный `Changed`.
3. Перед `add_private_comment` — сравнение отпечатка с последним скрытым digest (антидубль в `analyze_and_comment`).

LangGraph / Temporal — только при UI с resume HITL или durable wait на дни; на текущем масштабе достаточно cron + file checkpoints.

## 12. Corrective RAG — бот vs человек + Confluence (2026-08-28)

Два слоя IEK LLM после закрытия заявки (если был gap в KB):

| Слой | Модуль | Результат |
|:--|:--|:--|
| Сравнение | `learn_compare.py` | `aligned`, урок, что бот упустил → блок «Урок самообучения» |
| Вердикт по статье | `kb_gap_llm.py` | `new` / `supplement` / `skip`, `KB_INSERT` |
| Поиск статьи | `kb_dedup.py` + CQL | локальный корпус/черновик; если мало текста — `confluence_client.search_pages` |
| Журнал | `learn_journal.py` | `knowledge/learned/learning_events.jsonl` |

**Контуры:** `contour_enabled.*.kb_learn` (CRM выкл) проверяется в `should_auto_learn` и при разборе (`service_filter`).

**Модель learn:** `learn_llm.learn_kb_model()` → `IEK_LLM_LEARN_MODEL` / `IEK_LLM_SUPPORT_MODEL` (`iek/confluence-agent`).

**Reject → learn:** `rejection_reason` в index подмешивается в промпт; отклонённые коды не дополняются (`rejected_avoid`).

**Ревью UI:** Streamlit — полный черновик + KB_INSERT; Confluence push опционален (`auto_push_confluence_draft: false`).

**Документация:** `pipeline/IDEA_RAG_LEARNING.md`, `docs/pipeline/самообучение.md`, Confluence §3.1 + дочерняя «Самообучение AI-KB (Corrective RAG)».

**Backlog:** Jira, кластеризация паттернов, SQLite-метрики — см. IDEA §6.

### 15. Преданализ: тип, сервис, важность (Качанов Ю.А.)

Скрытый комментарий **всегда** заканчивается строкой классификации:

`Сервис: {id} · ветка · тип: … · важность: … · [рекомендации]`

| Поле | Авто | Правило |
|------|------|---------|
| TypeId (1008/1009/1010) | нет | рекомендация по тексту + prior |
| ServiceId (731 vs 732 и т.д.) | нет | рекомендация; инцидент ЛК → 731 |
| PriorityId (11/9/10/12) | **да**, только повышение | `--post` + `auto_set_priority_on_analyze`; не понижать |

Если prior заявителя другого контура, чем текст — `contradiction`, prior не используем, важность не ставим автоматом.

Код: `service_routing.check_service(prior=)` · тест `scripts/test_service_classification.py`.
