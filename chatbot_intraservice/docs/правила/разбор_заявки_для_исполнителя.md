# Разбор заявки для исполнителя (скрытый комментарий)

Цель: помочь **исполнителю** за 10 секунд. Клиенту не видно (`IsPrivateComment=true`).

## Формат (компактно, ~6–10 строк, без лишних переносов)

```
Результат преданализа IEK LLM · https://chatgpt.iek.local: …   ← единый связный текст (описание + факты + OCR через IEK LLM, без повторов и сырого OCR)
Контур: CRM / EDI / ЛК / БП … · этап: … · причина: …   ← этап и причина из LLM; category без маппинга — тоже здесь
Заявитель/партнёр: …   ← **только контур ЛК**; партнёр — только если найден
Проверки: adm/lk-admin/1С одной строкой через « · »
Контекст: …   ← вывод IEK LLM по ранее решённым
Похожее: #… · …
Комментарий для заявителя: …   ← 2–3 предложения без воды
Ссылки: …
Сервис: …   ← только в конце и только если контур после анализа ≠ ветка HD (ЛК/БП/EDI→1С)
```

Не писать в комментарий: `Категория: NS_…`, сырой «Скриншот (OCR): Действия Перейти…», дубль email заявителя=партнёра.
Шапка + ссылка Open WebUI = внутренняя модель IEK.
lk-admin: `учётка email` + дата входа; без Bitrix id и без мусорного login вроде Marketplace.

## Алгоритм разбора (1 линия)

1. **Контур** — lk / bp / **edi→1С** (электронный обмен, заказ поставщику, ADI). Сервис в комментарии — только при несовпадении с веткой HD.
3. **Факты** — кто пишет: `CreatorEmail`. Если `@iek.ru` — это **МРК** от имени партнёра; email партнёра брать из текста/скриншота (OCR), не путать с МРК. Из OCR выписать **номера**: заказ `ХИ…`, эл.заявка, счёт, GUID ЛК.
4. **adm / lk-admin** — контур **bp**: ServiceId 833/827 **или** явный bp.iek.ru / **IEK ID**.  
   Контур **lk** (731/732, API каталога, mailer@iek.ru): поиск в Bitrix  
   `lk.iek.ru/bitrix/admin/user_admin.php?find=<email>&find_type=email` (`LK_ADMIN_COOKIE`).  
   Даже если HD поставил 732, а текст про bp — проверить adm и предложить → 833.  
   Для чистых заявок ЛК (заказ, резерв) adm.bp не вызывать; lk-admin — да, если есть email.
5. **1С** — только при номере заказа и теме про резерв/заказ; если не проверяли — **не писать** строку про 1С.
6. **Связанные заявки** — поиск HD по заказу/счёту/эл.заявке/GUID. Совпадения (МРК + партнёр и т.п.) подсветить в скрытом комментарии; более позднюю подчинить к более ранней (`ParentId`), инициатора ранней добавить в **наблюдатели** поздней.
7. **Где API-ключ** — подсказка по контуру (см. ниже).
8. **KB** — решение и статьи **только** если есть в WEBKB; иначе не писать.
9. **Просрочка** при статусе «В процессе» / «Ожидание ответа»: если в lifetime есть свежая эскалация «До просрочки» — всё равно скрытый разбор; затем дедлайн **+1 день** и **открытый** ответ заявителю. Без эскалации — skip.

### Проверка ServiceId (HelpDesk)

| ServiceId | Ветка | Когда |
|:--|:--|:--|
| **731** | ЛК партнёра → «Инцидент» | lk.iek.ru: поломки ЛК |
| **732** | ЛК партнёра → «Запрос на обслуживание» | lk.iek.ru: заказы, резервы, партнёр, API каталога (учётка от поддержки) |
| **833** | Бизнес-платформа ЦКГ → «Запрос на обслуживание» | bp.iek.ru, **IEK ID**, авторизация/пароль, API-ключ, oauth/ticket, ЦКГ |
| 713 | родитель ЛК | — |
| 827 | родитель БП | — |

**Правило:** если контур **bp**, а заявка в **732** (ЛК) — в отчёте указать «→ 833?».  
Если **adm** нашёл учётку на bp, а ветка ЛК — сильный сигнал переноса на **833**.

### Где генерируется доступ к API

| Контур | Где ключ / доступ | Кто создаёт |
|:--|:--|:--|
| **bp.iek.ru** | Профиль → [API keys](https://bp.iek.ru/profile#api-keys) | Пользователь сам (после регистрации на bp) |
| **bp API auth** | `username=ticket`, `password=<API-ключ>` | — |
| **lk.iek.ru API каталога** | Учётка «внешний пользователь API» | **Поддержка WEB** создаёт в lk, пароль на email mailer@iek.ru |

Не смешивать: партнёрский API ЛК ≠ API-ключи bp.iek.ru.

### adm (БП)

`https://adm.bp.iek.ru/main?search=<email>` — есть ли учётка, LEGAL/PERSONAL, ИНН.  
Вызывать при тексте про **IEK ID / авторизацию**, даже если ServiceId=732.  
**Не вызывать** для чистых заявок ЛК (заказ, резерв в пути).

### МРК vs партнёр (только ЛК)

Если `CreatorEmail` оканчивается на `@iek.ru` — заявитель сотрудник IEK (МРК), пишет за партнёра. Email партнёра на скриншоте/в письме вывести отдельной строкой **только в разборе заявок ЛК** (ServiceId 731/732). Для 1С, БП, CRM и прочих контуров строку «Заявитель/партнёр» не добавлять.

### Подчинение дублей (ParentId)

Модуль `src/task_linking.py`. **Не путать** со строкой «Связанные заявки» и «Похожие» в комментарии — это справка.

**Когда ставится ParentId** (при `link_related_on_post` и «Подчинение» для контура):

1. В тексте/OCR найден **сильный токен**: номер заказа/счёта ХИ…, эл.заявка `0000…`, полный номер тендера `T260831-191291` (для CRM **не** GUID компании и **не** префикс `T260831` без суффикса).
2. IntraService `search=` находит другие заявки с тем же токеном.
3. Из них в подчинение попадают только: **тот же календарный день** (`Created`), **открытый статус** (31/38/121/27/46/120), **тот же ServiceId**.
4. Родитель — **самая ранняя** по `Created` в кластере; остальные → `ParentId`.

**CRM по умолчанию выключен** (`link_related_by_contour.crm=false`): GUID контрагента повторяется в заявках годами.

Массовый инцидент (много пользователей, одна проблема в один день): совпадают заказ/эл.заявка/полный тендер → все открытые заявки за день подчиняются к первой.
