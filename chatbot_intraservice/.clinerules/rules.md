# .clinerules — Правила разработки через ИИ (в т.ч. на слабых моделях)

> Применяются ко **всем** запросам к ИИ для работы с проектом
> `chatbot_intraservice`. Не меняют проект — описывают **подход** к решению задач.
> Цель: даже на слабых моделях (DeepSeek v4 flash, Luna) получать стабильный результат,
> не терять историю решений и не растирать контекст.

## 1. Слабые модели — как получить хороший результат

1.1. **Контекст = дробя.** Слабые модели часто кладываются на границе длины промпта
(«слишком длинный» → fallback). До передачи кода в модель:
- выделяйте **только нужный фрагмент** (1 функция / 1 класс / 1 файл);
- отбрасывайте тесты, логи, `_probe_*`-файлы и прочие артефакты;
- если контекст растёт, разрезайте на порции `< 3–4k` токенов.

1.2. **Минимум системного промпта.**
- системная роль — 1–3 короткие фразы;
- примеров (few-shot) — максимум 1–2, без пояснений;
- инструкции — конкретные глаголы: «Измени только строки X», «Верни diff»,
  «Не рефакторь заодно».

1.3. **Пошагово и мало.**
- один LLM‑запрос = одна операция (read / edit / grep / test);
- несколько независимых запросов — **параллельно**, а не в одном «спагетти‑промпте»;
- каждый шаг проходит **микровалидацию** (компиляция / линтер / тест) прежде читать дальше.

1.4. **Итеративный рост.** Сначала «работает», потом «чисто», потом «оптимизировано».
На слабой модели сразу делать всё — приводит к пропуску.

1.5. **Запасной план.** Если модель не справилась (пустой / «слишком длинный» /
несвязный ответ) — переключиться на fallback‑модель (`iek/gpt-oss-120b`),
сократить контекст в 2× и повторить.

## 2. Планирование и разложение задач

2.1. **Plan first.** Каждая задача начинается с плана:
1. сбор контекста (read_files / search_codebase / fetch_web_content);
2. анализ требований;
3. список правок с указанием файлов;
4. порядок выполнения (зависимости между шагами);
5. план проверки (компиляция + тесты).

2.2. **Не редактировать всё сразу.** Правка = один editor‑call на одном файле/блоке.
Перед правкой — read_files нужного диапазона.

2.3. **Независимые действия — параллельно.** read_files / поиски / запуск тестов
без зависимости между собой выполняются в одном сообщении (batch mode).

2.4. **Микрозадачи.** Крупную задачу дробим до правки, проходящей `python -c "import"`
или одним тестом.

## 3. История разработки и принятых решений

3.1. **Decision log.** Все архитектурные и тактические решения фиксируются в:
- `docs/pipeline/решения.md` (текущая сессия + важнейшие решения);
- `.clinerules/decisions.md` (долгоживущий лог решений по ИИ‑разработке).

3.2. **Handoff обязателен.** В конце сессии (и при смене задачи > 30 мин)
обновляем `docs/handoff.md`:
- что сделано;
- что сломано / заброшено;
- блокеры;
- следующий шаг / коммит.

3.3. **Чекпоинты.** Перед каждым серьёзным изменением делаем `git stash`-safe коммит
(или `git add -A && git commit -m "..."`) с понятным сообщением:
```
type(scope): кратко
```
где type ∈ {fix, feat, docs, test, chore}.

3.4. **Прозрачность моделей.** Текущую «запрошенную» и «реально используемую»
модель логируем в `_analysis_*.json` (`model_requested`, `model_resolved`).
Это нужно для отладки fallback и для истории.

3.5. **Артефакты не в git.** `_probe_*`, `_tmp_*`, `_out.txt`, `rebuild_kb_drafts_result.json`
игнорируются (`.gitignore`), но используются как рабочие файлы в текущей сессии.

## 4. Тестирование и проверка

4.1. **После правки** запускаем:
```powershell
python -m pytest -q
```
(и/или заложенный в задачу набор тестов).

4.2. **Линтер / компиляция.** Если проект имеет ruff/flake8 — применяем.
Минимум — `python -c "import src.<module>"`.

4.3. **No regressions.** Если тест падает — не двигаемся дальше, пока не починим.

## 5. Работа с LLM API

5.1. **Не передаём OWUI-имена `*-web-helper`** как `model` в LiteLLM.
Для HD‑пайплайна используем `iek/confluence-agent` + REST-prefect Confluence
через `src/confluence_tools.py`.

5.2. **fallback модель** — `iek/gpt-oss-120b` (через `llm_client.resolve_model()`).
`confluence-agent` отключён с 2026-09 — resolve подставит доступную.

5.3. **AI-KB.** В черновики попадает только блок `KB_INSERT`;
человек апрувит в Streamlit.

## 6. Контур и секреты

6.1. `INTRASERVICE_*` / `CONFLUENCE_*` / `IEK_LLM_TOKEN` — только в `.env`,
никогда не кладём в git.

6.2. `contour_enabled` / `disabled_service_ids` уважаем — не включаем L1 теоретически,
если контур выключен.

---

*Эти правила заменяют любые «умные» попытки «сразу всё сделать».
На слабой модели главное — не объём, а **структура**.*
